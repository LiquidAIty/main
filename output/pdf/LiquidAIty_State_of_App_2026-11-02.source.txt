@H1 6 Main submission and reply handling

The current path is MainProjectChat to useAgentBuilderMainChat to mainSessionClient to the authenticated Main route to HermesGateway and the receiving profile. The frontend opens the Project once and retains the handles returned by Hermes. It submits unchanged user text and attached images. The backend checks Project access and the receiving profile, then forwards prompt.submit through the existing client. [R01 R02 R03 R04]

The backend route no longer explicitly performs session.list, session.resume and session.history before every chat submission. One session.list helper remains for the preserved Card terminal identity check. Treating that terminal check as proof of a per chat history wait would be inaccurate. Hermes's client can still attach an unattached conversation on its own socket when a request requires it. That is Hermes's implemented protocol behavior, not a new application session manager. [R22]

For an @Name request, the application resolves an exact saved address among the current wired roster. This is structural addressing, not a semantic agent selection policy. Ordinary Main delegation through message_agent is a separate path in Hermes. Neither should be substituted silently for the other.

The response listener filters by receiving profile, conversation and admitted request. It forwards text deltas and the completion. After sending the completion and ending the HTTP response, it calls the existing conversation store asynchronously with the user message and assistant reply as one completed pair. The storage code does not invoke ThinkGraph. The earlier user requirement that storage should not delay model submission is represented in this ordering. [R01 R09]

@H2 An unresolved later reply boundary

The listener belongs to the initial HTTP request and is detached when that response closes. Events must match its admission identity. That is good protection against attributing another profile's answer to the current message, but it does not establish how a later independent Main wakeup from an asynchronous Bot reply becomes visible in an idle foreground chat.

The correct next step is a bounded live acceptance scenario: Main actually calls one connected profile, the recipient responds after Main's initial response, and the later result appears under the correct identities. If that fails, the repair belongs at the existing Hermes client and view subscription boundary. A new reply poller, fake completion buffer or separate Bot runtime is not justified by this report.

@H2 Submission while work is active

The frontend tracks multiple active streams and does not simply reject every new message because one request is active. It retains per request identity and delegates admission and steering semantics to Hermes. This is source evidence, not a completed concurrency test. The owner's never stop a chat requirement should be tested with real successive user input, not inferred from an enabled Send button.

@H1 8 Conversation storage and the database question

Hermes stores each inspected profile's state in its own ordinary SQLite state.db. The Main file was about 5.86 MiB at inspection. This file format is not a model context window, an embedding, or a holographic memory system. The database can retain more text than any one model request needs. Its size alone says little about the time required for inference.

The inspected Main database contained messages and full text indexes, sessions, system prompts, model usage, queued admissions, turn leases, runtime epochs, routing, compaction locks, hygiene state, delegation and worker records, and room related tables. Some tables exist because Hermes supports features that this app does not use. Their presence does not establish that those features were exercised. Removing tables because their names look unnecessary would break a storage contract without solving the model-input policy. [R26 R27 R40]

Engraphis also uses SQLite, but its database contains workspaces, events, memories, entities, edges, embedding state, vectors, graph indexes and source import/provenance records. The current Python integration resolves the authenticated Project's owner in PostgreSQL and uses db/users/<owner>/engraphis.sqlite. The Project remains a workspace inside that owner's database. This is already implemented in current source, despite older PLAN wording to the contrary. [R10]

@H2 Why replacing state.db with Engraphis is not a simple speed fix

The two databases share a storage technology, not a schema or execution API. Hermes expects specific admission, conversation, lock and replay operations. Engraphis expects its own memory and graph operations. Pointing one at the other's file would not implement the missing contracts.

The current system does retain conversation material in two places for different purposes: Hermes's execution transcript and the application's Project conversation source. This is real duplication and deserves a deliberate long-term storage policy. It is not a reason to silently delete either store. A future consolidation would need a supported Hermes transcript backend or an explicitly reviewed change, plus proof that runtime bookkeeping, original-source recall, and other surfaces still work.

The immediate fix for a book-sized prompt is to select what enters the request. The ordinary Hermes transcript loader reads active messages for a conversation; compaction-archived messages are excluded. That is already distinct from a full display-history read, but it is not a strict three-pair selection. [R26 R27]

@H2 Application persistence is outside the latest reply critical path

The current Main route ends the response before starting the completed-pair save. The application store transports the pair to Python, which writes the existing Engraphis event ledger. This path does not invoke ThinkGraph extraction. In the latest measured Main run, the provider call consumed 12.2 seconds while application admission and final delivery were subsecond. Those measurements do not support assigning the provider delay to the later application save.

There is nevertheless a scale concern in the storage implementation. The conversation operation currently loads and sorts all matching message/status events even when appending, including calculating the next sequence. Initial UI history likewise returns the entire application conversation. This can grow expensive as a chat becomes very long. It should be measured and then bounded through the existing ledger/index/pagination owner, not solved by adding another conversation store. [R09]

@H2 File concurrency and deployment

SQLite allows many readers but one writer at a time per database file. Short transactions and owner-partitioned files can work well for a local or modest service. Multiple servers opening the same file over a network share are a different and unsafe deployment assumption. A client/server database or explicit state-host partitioning is preferable when the workload requires many independent concurrent writers to one shared logical database. That is a deployment decision, not evidence that SQLite caused today's latency. [E14]

Engraphis currently has a module-global service lock and caches each opened owner service until shutdown. That could serialize unrelated owners in one Python rails process. The report recommends a contention measurement before changing it. The proper unit, if correction is needed, is the owning service/connection; no new graph or indexer is implied.

@H1 9 History selection and continuous conversation

The selected goal is continuous conversation without an ever-growing replay of all prior text. Keep three recent completed exchanges for local continuity, and make older source recoverable through authorized retrieval. The current question, profile instructions, tools, selected graph context and current operation's necessary tool results remain distinct inputs.

A pair must mean a complete user-led exchange, not two arbitrary database rows. Tool calls, tool results, assistant iterations, steering messages and final answers can make one exchange span several rows. A naive last-six-rows slice can create invalid tool sequences or remove the user question that gives a result meaning. The policy therefore needs a semantic unit consistent with Hermes's actual transcript structure, while the implementation remains structural rather than a keyword planner.

Keeping all user messages verbatim in every request is not indefinitely bounded. It also loses meaning if the answers they refer to are omitted. A message such as use the second option depends on an earlier answer. Preserve all original user messages in durable storage; retain the most recent three complete exchanges inline; retrieve the earlier relevant question and answer together when needed.

@H2 What Hermes already provides

The default compressor performs threshold-based compaction and retains a recent section. The saved 32000 threshold is an absolute trigger cap, not a guarantee that every request is below 32000 tokens. The selected lean strategy has its own tail budget and protection rules. min_tail_user_messages is a minimum anchor, not a maximum history count. Changing it to three would not implement the requested last-three-only policy. [R29]

Hermes also exposes ContextEngine.select_context. It can replace the message list for a particular provider request without mutating the durable transcript. This is the kind of existing seam relevant to bounded recent history plus retrieval. It is not a ready-made configured three-pair feature in this checkout. The default implementation does nothing, and invalid or failed selection falls back to the unchanged request. A strict policy would have to address that behavior explicitly rather than assume the existence of a hook is acceptance. [R28]

pre_llm_call is different: the inspected documentation describes it as injection, not replacement of the history list. It can append a graph view, but it does not by itself remove already assembled history. The report specifically rejects using the two interfaces interchangeably.

@H2 The never stop a chat requirement

The product requirement is not that arbitrary computation takes zero time. It is that growing history must not force the user to discard work, start a new conversation, or lose the ability to submit or steer. For ordinary conversation, input selection should not require an extra summarization model call before every answer. For long tool-intensive work, the active task's state must remain valid and Hermes's own controls must continue to own admission and interruption.

A complete acceptance test should distinguish: immediate acknowledgement that the UI accepted the user's input; actual Hermes admission; first useful model text; completion; and durable storage. A fake answer saying work has started is not an acknowledgement protocol and must not be used to hide a stalled model.

@H1 10 Retrieval and the graph memory product

The reasonable starting proposal is three recent complete pairs plus up to five relevant older source passages, with graph context selected by the existing graph owners. Twenty retrieval candidates can be useful for finding those five passages; twenty candidates need not become twenty passages in the model input. These numbers control different stages and should never be hidden behind one ambiguous memory setting.

An embedding is a numerical representation used to search for semantically related text. The answer model receives selected text and references, not the vector itself. Semantic retrieval can handle paraphrases; lexical or exact identifier matching is useful for tickers, filenames, error strings and quoted requirements. A hybrid strategy can improve recall, but adds work and must be evaluated on the app's actual questions. This is a research lesson, not a proposal to install Qdrant or another store. [E10]

Current source already contains search_source_exchanges, returning five matches by default with a permitted range of one through twenty. It asks Engraphis for up to one hundred episodic candidates and an eight-thousand-token internal budget, then filters for indexed conversation-source chunks. The result includes original source pointers. A read-only count found sixty-seven conversation-source records in the tested Project. This proves a stored index exists, not that every raw conversation has been indexed. [R09 R11]

The ordinary Main route does not call this retrieval function before prompt submission. Its existence must not be described as a complete automatic RAG path. The current source index is normally produced by the accepted extraction/settlement owner, while automatic stored-pair delivery is disconnected. Connecting retrieval responsibly therefore requires proving both source coverage and the receiving model input, not merely adding a search call.

@H2 Graph memory and raw source serve different purposes

Thinks should capture useful reasoning and operational knowledge with exact source links. Knows should retain a sourced observation and its evidence, with interpretation separate. Raw conversation remains the faithful source when the user asks what they actually said or when an earlier extraction omitted something. None is an adequate substitute for all the others.

The graph map is a compact view of the visible Entity/Relationship structure at a turn. It is orientation, not evidence that every graph record was read. The approved displayed top Jev result must not silently become a hidden set of extra candidate records. A retrieval failure must not relabel the most recent record as the most relevant one.

@H2 Retrieval quality is a release criterion

Evaluate the selected design against original corrections, exact identifiers, old ideas, cross-Project contradictions, dated Knows and source-linked Thinks. Test whether the answer can cite the actual passage and whether no result is reported honestly. A greeting should not require a retrieval model or inject unrelated memories just to fill a quota.

RAG is not a substitute for exhaustive reading when the user asks to audit an entire document or codebase. Long-context research has found cases where complete-source input performs better than retrieval, and retrieval research has found benefits from more final evidence chunks on some workloads. The app should select the appropriate method for the task instead of asserting a universal five-chunk optimum. [E11 E18 E19]

@H1 11 ThinkGraph and KnowGraph completion

The approved Think workflow has a meaningful existing foundation: full conversation events, explicit pair reading, chunk snapshots, source indexing, preparation and settlement. These are useful owners worth preserving. The ordinary chat save-triggered handoff was removed and is not connected in the current stage. Successful direct ThinkGraph chat therefore does not prove automatic Think production from a newly stored Main pair. [R09 R11 R14 R35]

The next approved implementation should remain one-way and storage-owned: a newly completed pair becomes available to the existing preparation and extraction path, which persists source-linked Thinks through Engraphis. Main's Hermes completion receipt, usage events, and arbitrary latest-two-row guesses must not become a new pair authority. Do not replay old test history to manufacture apparent automatic success.

KnowGraph is an ordinary saved Hermes profile for research. The retained requirement is one sourced observation per Know, with its source document and exact evidence passage, separate bounded interpretation, and the relevant Entity reference. Queue acceptance is not persistence. The acceptance path must read the actual Know back after processing and show the correct citation in the inspector. No automatic research dispatcher is authorized by a researchRequested flag.

@H2 Live graph presentation

The source review found a Project-scoped ThinkGraph event stream, but the only production notification caller found was the route's retirement action. Writes through tools and settlement were not observed to emit that existing notification. KnowGraph's hook refreshes on initial load and confirmed deletion; its claimed change-notification behavior was not found as a corresponding subscription in the inspected hook. [R12 R13]

This is a product gap: a successful committed write may not automatically appear in the open graph. The smallest proposal is to complete the existing provider-commit notification boundary. It is not to add a timer, poll for every queued write, or invent a second event bus. The test must prove the right Project refreshes after real persistence, and an unrelated Project does not.

@H2 Preserve the source citation idea

Source chunks and Think-to-source citations survived the recent cleanup. They are not equivalent to the rejected Main-linked handoff wrappers. Removing those wrappers should not silently delete the useful ability to recover the exact original exchange. The report's preservation ledger keeps those capabilities separate so that cleanup does not erase the product's central memory promise.

@H1 12 CodeGraph and structural understanding

CBM is the source-structure authority. It can map callers, files, imports and definitions, while source annotations explain stable feature membership. It does not prove runtime success, interpret the user's product intent, or authorize an architecture change. Its watcher metadata is not a reason to pause chat, reinstall an indexer, or repair a provider unrelated to the current task.

The application-published CodeGraph read corridor is different from repository-development CLI access. Saved product profiles should retain only their actual granted operations. Codex development uses the installed CLI under the repository's current rule. Removing one transport from developer practice must not silently remove the product agent's granted provider access.

The report used CBM as a directional accelerator and direct source as the final authority. Runtime and vendor boundaries were inspected directly. A structural query that returned no matching symbol was not taken as proof of absence; the exact routes, registrations and relevant source were read.

@H2 Why more documentation has not automatically solved understanding

Documentation helps only if it is discovered, current, correctly interpreted and connected to proof. This repository contains both strong explicit design instructions and stale current-state descriptions. Merely adding more prose can increase ambiguity if contradictory owners remain described as current.

The separately requested repository skill is designed to change decision behavior: recover the requested observable result, locate its owner, identify the preservation set, classify evidence, and keep alternatives as proposals. It does not replace source inspection or make the agent infallible. It explicitly forbids treating familiar patterns as permission to normalize the user's different design.

The skill is stored at .agents/skills/understand-project-design/SKILL.md with a direct AGENTS reference. This keeps the instruction near the repository and makes it discoverable. It does not add hooks, scripts, runtime interception or another status ledger. The format validator passed. Its behavioral value still requires forward evaluation on realistic requests.

@H1 13 Project and user isolation

A reusable agent definition is not a live conversation. The same user can reuse one actual profile across many Projects without needing a cloned profile for every Project. Each Project nevertheless needs distinct conversation state and the correct Project-specific credentials, memory scope, files and wired authority. Shared configuration must not become shared private content.

The current application resolves Bot Chat by the receiving profile and fixed title. Hermes's recipient lookup also finds that profile's Bot Chat. LiquidAIty's Project ID is not part of that recipient lookup. Separate browser Projects therefore do not establish separate Hermes conversation histories. [R01 R23 R25]

There is a second coupling: opening a Project writes its roster and internal MCP credential into the profile's configuration. Another Project using the same profile may have different wires or Project scope. The source consequently exposes a potential last-publication-wins conflict. This audit did not reproduce a cross-Project leak or change two Projects concurrently; it identifies the coupling that must be resolved and tested before such use is supported.

Cross-user profile identity is also currently constrained globally. assertCardProfileOwner requires exactly one owner among references to a profile, and the saved profile/Card binding lacks an account namespace. Default Projects seed fixed profile names. A second owner can therefore encounter a conflict rather than an independent private instance. The conflict rejection is useful protection; disabling it would not implement tenancy. [R05 R08]

@H2 Required owner decision

Choose the deployment and profile ownership unit before implementation. A credible design may use user-owned Hermes profile homes with separate Project conversations, while shared templates contain only reusable configuration. Tool credentials and context must remain request/conversation scoped under the supported runtime authority. If Hermes cannot represent a required isolation boundary through existing public interfaces, state that gap plainly and seek approval for the smallest extension. Do not hide it behind a second application session manager.

@H2 Acceptance before multiple Projects are claimed

Use two Projects with deliberately different private content, graph sources and wires. Exercise the same human-facing agent name concurrently. Verify the actual Hermes conversation, tool principal, roster and retrieved source scope for each turn. Then repeat with a second user. A title or a different UI tab is not enough. This is a core privacy requirement, not an optional edge case for a hosted product.

@H1 14 Scale and the ten million Project question

Ten million saved Projects do not require ten million resident agents. The durable configuration, conversation and memory can be stored while only active Projects consume execution capacity. The owner's requirement that all wired agents are prepared when an open Project becomes usable can coexist with this: prepare that active Project in parallel, not every dormant Project in the system.

The scale model must distinguish registered users, users currently interacting, open Projects, simultaneous model generations, background tasks, database writers and tool processes. Ten thousand simultaneous users are not necessarily ten thousand simultaneous model calls. Conversely, if they all submit at once, the infrastructure and provider must admit or queue that demand honestly; a fast single-user test proves none of this.

For illustration only, if ten thousand active users each send one message per minute, the average arrival rate is about 167 requests per second. At a twelve-second average service time, roughly two thousand requests would be in service on average before adding tool or background work. This is arithmetic under stated assumptions, not a capacity measurement or deployment sizing recommendation.

The current local stack has owner-specific Engraphis files, but a global lock can still serialize operations inside one rails process. Hermes profiles and Bot Chats are not yet Project-isolated. Application authentication lacks demonstrated production abuse controls. None of these facts requires replacing the current local runtime to continue feature work, but all matter before a shared public launch.

@H2 A staged scale path

First certify a single-owner local release. Then prove two concurrently active Projects. Then prove two users with negative isolation tests. Next run a bounded concurrent workload using the chosen deployment topology and provider limits. Only after measuring resource use, queueing, errors and recovery should the supported concurrency be advertised. Large-user-number aspirations should inform clean boundaries without becoming an excuse to build a speculative distributed framework today.

@H1 15 Authentication privacy and public boundaries

The current app has meaningful authentication protections: cryptographically random session tokens stored as hashes, server-side expiry, HttpOnly cookies, production Secure cookies, SameSite behavior, password hashing, and owner checks. Terminal upgrades check credentials, Origin, Project ownership and the precise profile/conversation relationship. These are existing positive controls, not unnecessary wrappers to remove during performance work. [R16 R17]

The backend binds to loopback. Internal Python rails and graph services rely on the local network boundary rather than browser-style per-request authentication. That is a deliberate local architecture, not a claim that those endpoints are already exposed to the internet. A deployment that publishes them directly would change the security model and needs a separate design and proof.

Before public signup, account abuse and recovery require attention. The reviewed auth routes contain no demonstrated login/signup throttling, general user budget enforcement, verified-email flow or password-recovery endpoint. There may be alternative identity-provider integrations outside the reviewed path, but their presence must be established rather than assumed. Use one chosen identity owner, not an additional shadow user store.

@H2 Tool and retrieval authorization

The model's request text is untrusted as an authorization source. User and Project scope must come from the authenticated application. An agent title or a supplied Project UUID does not authorize access. Credentials should be obtained from the correct profile and active scope; process-global configuration must not accidentally select another user's token or workspace during concurrent work.

Vector indexes are not inherently private. Embeddings and retrieved text retain the sensitivity of their source. Retrieval must enforce owner and Project filters before supplying content, and source references must be checked again when expanded. A shared public example Project must not include the author's private history or credentials.

@H2 Data deletion and export

The current Project deletion route removes application relational rows, but the reviewed path does not remove all related Engraphis, Graphiti, Hermes or filesystem data. Some data may intentionally be shared or retained. Therefore the UI must not promise total data erasure until exact ownership and retention semantics are defined and implemented. This finding does not authorize deleting anything during this audit.

The release decision must specify archive versus delete, export format, recovery window, shared-resource treatment and backup responsibilities. Test those operations on a deliberately disposable fixture and prove unrelated Projects survive. Do not use the user's actual working Project as the deletion test.

@H1 16 Startup packaging and operational truth

The current full launcher is a development workstation path. It uses PowerShell, local Python environments, Docker Compose for the root data services, a backend build, Python rails and MCP readiness, the Vite frontend and companion services. Its readiness ordering is useful: the UI is not started before the required backend/rails/catalog checks. [R19]

The current root scripts do not invoke the optional WorldSignals startup branch in start-dependent-services.ps1. WorldSignals may already be running, but the canonical launch sequence alone does not prove it started that service or supplied its operator credential. The release bundle must explicitly decide whether this module is included or optional.

Process health endpoints are narrower than functional readiness. Backend and rails status responses indicate liveness. MCP exposes more detailed family availability, but a successful readiness response should not be interpreted as every provider and tool being usable by every selected profile. The release test should read actual provider/catalog detail and exercise the promised capabilities.

@H2 Local installed product versus hosted service

A production client build is not an installer, a reproducible fresh-machine setup or a supported hosted deployment. A local release needs a documented supported environment, controlled installation and update behavior, credential onboarding, durable data placement, startup failure messages and a recovery rehearsal. A hosted release adds private-service networking, tenant isolation, quotas, shared resource coordination, observability, backups and operator responsibility.

Do not make cloud-scale infrastructure a prerequisite for an honestly scoped local preview. Do not call a local preview a cloud-ready service. This is the first business and release-scope decision in the waterfall plan.

@H1 19 Runtime conclusion and the boundary to freeze

The ordinary local Main and direct-agent conversation path is a useful foundation. The app does not need another generic runtime to move forward. Hermes owns the model/tool loop and Bot machinery; the application should preserve the small transport and presentation boundary that now works.

@H1 20 Hermes Desktop dashboard and Bot Mode

The report distinguishes three things often called a Hermes UI: the installed official Desktop application, the installed official browser dashboard, and independent community web applications. They do not have interchangeable implementations. The installed source is the authority for LiquidAIty's actual integration; current upstream documentation is comparative evidence, not proof that this checkout was updated.

@H2 Official Desktop

Hermes Desktop uses the existing agent configuration, profiles, tools and session state. Its gateway client provides transport, profile routing, attachment tracking, request budgets and protocol handling. The client conditionally attaches a conversation on its socket before an operation that requires attachment. It records an attached snapshot so the same operation need not blindly attach every time. [R22 E01]

The Bot UI identifies a profile's titled Bot Chat. On explicit navigation to a Bot, Desktop can perform a lookup and force a fresh resume for viewer hydration. These are view-opening actions, not evidence that every user message should trigger an application-owned lookup/resume/history sequence. The distinction matters because earlier work confused the costs of opening a viewer, delivering work to a profile, and assembling the model's conversation history. [R23]

The application currently reuses HermesGateway from that Desktop code. That is evidence of reuse, not proof of a stable third-party public SDK contract. Future updates need exact compatibility checks around the imported client and gateway ticket code. The current working import should be pinned and preserved during feature work rather than replaced with a new protocol after every upstream change.

@H2 Official browser dashboard

The installed web directory is a Vite/React dashboard for configuration, keys and session monitoring. Its ChatPage embeds the Hermes terminal UI through xterm and a PTY WebSocket; it does not simply duplicate the Desktop React chat implementation. Its Sessions page loads transcript messages when a session is expanded and can navigate into chat using the stored session. [R31 R32]

This yields a useful lesson: a UI can expose Hermes execution without becoming the agent runtime. It does not mean LiquidAIty should replace its accepted Main chat and Cards with a terminal. The owner wants a different product surface, with the same underlying execution owner.

@H2 Bot to Bot delivery

The installed Bot path is message_agent through Bot live delivery into the recipient's authority. The authority resolves that recipient profile's Bot Chat and can create it when absent. An open chat viewer is not a prerequisite for delivery. The human composer prompt.submit interface and internal automation bot_relay.deliver interface are not interchangeable names for the same user operation. [R24 R25]

The Bot implementation contains its own receipt and polling behavior in places. A legitimate dependency timer and an unnecessary application pre-send wait are different findings and require different evidence.

@H2 Hermes Projects

Hermes has a real per-profile projects.db containing named Projects, folders, primary paths, an active Project pointer, optional board association and repository cache. Workspace tools can change the calling GUI session's working directory without moving the global selection for other chats. However, Bot recipient resolution still calls get_session_by_title for Bot Chat inside the recipient authority. The Project store does not automatically add LiquidAIty's authenticated Project identity to that lookup. A workspace folder is not equivalent to a user-authorized application Project or its graph workspace. @H1 21 Open WebUI comparison

Audited upstream snapshot: f7ac7ee10962ddec0017f5c29b6740d9b9c5faca, dated 29 October 2026 UTC. This is not a version installed in LiquidAIty. The comparison reviewed model/chat/user-memory schemas, context compaction, persistence and scaling guidance.

Open WebUI separates reusable model/prompt presets from user-owned chats. Its memory records have a user identity and owner checks. The inspected implementation chooses safe user/tool boundaries and separates system instructions. The default is not evidence that full replay is universally desirable. @H1 22 LibreChat comparison

Audited application snapshot: f4154b649efa37e1345ccc517a4d8d1ed2178c82, dated 31 October 2026 UTC. Audited agents-library snapshot: 708c9118f478a84f28e8e253148a373b49fec191. The review covered agent and conversation schemas, context retention, memory extraction, RAG, steering and resumable streams.

LibreChat keeps agent definitions separate from user/conversation/Project records. Its recent-turn retention is particularly relevant: a retained user-led turn includes the following assistant and tool messages through the next human-authored message. This protects tool integrity better than slicing arbitrary rows. Its retention option affects compaction; it should not be mislabeled as a permanent last-N-only policy. [E03a E03b E03c]

The agents library uses pressure-aware handling of already-consumed tool results before more expensive compaction or truncation. Current outputs that the assistant has not yet used are treated differently from old consumed observations. LiquidAIty can use this as an acceptance principle without transplanting LibreChat's message engine. [E03d]

LibreChat's memory.messageWindowSize controls the recent messages reviewed by an optional memory-extraction agent. It is not the number of messages sent to the main answer model. This distinction directly supports separate, explicit UI labels for history, retrieval and background learning. A single Memory 5 control would be misleading. [E03e]

The inspected file-search path retrieves five candidates per file, combines results and retains ten overall. It scopes user attachments differently from shared agent resources. These are concrete defaults for that path, not a universal ideal for LiquidAIty. Retrieval count, history count and memory-extractor count remain independent. [E03f]

LibreChat defines queue, steer and interrupt behavior and checks the executing run's identity. It can detach generation from a browser connection using resumable streams; multi-instance coordination uses Redis. Its documentation explicitly distinguishes surviving a client disconnect from surviving a generating server failure. The useful lesson is precise guarantees. The wrong lesson would be to add its job manager, stream store or queue to LiquidAIty when Hermes already owns those responsibilities. [E03g E03h]

**Adopt as ideas:** complete-turn retention, truthful admission controls, exact execution attribution and authorized retrieval. **Do not adopt automatically:** another generation engine, a memory-extraction model on every request, or a new RAG service that duplicates Engraphis.

@H1 24 Letta comparison

Audited current harness snapshot: letta-ai/letta-code at 3b7e3ffcf16d6ba4880f7a697261837000221320, dated 2 November 2026 UTC. The current letta-ai/letta repository redirects readers to that harness. Older server architecture should not be presented as the inspected current implementation. [E05a]

There is genuine system complexity, but repeated rebuilding of a thin Bot integration was not an unavoidable consequence of the user's design. Some checkpoints were described more confidently than their evidence allowed, and subsequent work inherited those assumptions. Contradictory documents and changing source made later understanding harder rather than automatically better.

The report cannot diagnose a hidden training mechanism or claim this behavior occurs on every project. It can identify the observable errors and the controls needed to prevent recurrence. A new skill is useful only if the next edit actually follows it. The right proof is fewer unjustified changes, correct ownership, preserved features and accurate acceptance claims, not another assertion of understanding.

@H2 Whether to keep using Codex or switch

The owner owes no loyalty to a tool that consumes the project's budget without delivering reliable value. Switching to Claude, using it as an independent reviewer, or comparing both on the same bounded task are reasonable options. This report does not claim one model will necessarily perform better, and it does not invent comparative pricing or performance evidence.

The case for continuing here is narrow and testable: the current session has recovered working chat, produced profile-specific evidence, identified real gaps without changing production during the audit, and preserved a portable review packet. That becomes a reason to continue only if subsequent work stays within scope and reaches real acceptance with less rework. The owner's project and artifacts should remain portable to another engineer or assistant.

@H2 Recommended next owner decision

Choose the first release envelope and one next waterfall stage. My recommendation is to preserve the recovered runtime, prove Card-to-Hermes configuration parity, then implement the selected history/retrieval policy through an explicitly approved existing boundary. Do not start another general runtime rewrite. If the first release includes multiple independent Projects or users, schedule isolation as a mandatory gate before that release, not as an afterthought.

The report is not a promise that every remaining feature is small. It is a way to prevent all remaining work from becoming one undefined refactor. The owner should be able to accept or reject a stage by its observable result and preservation evidence.
